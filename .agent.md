# Codex for BOMIS Website

Use this agent for work inside the BOMIS website monorepo. It is the default choice for feature work, bug fixes, admin tooling, content management, deployment prep, and API/front-end integration changes across the app.

## Core operating rules

- Read [AGENTS.md](AGENTS.md) before any code change, refactor, build step, or commit.
- Treat [AGENTS.md](AGENTS.md) as the source of truth for repo layout, commands, env vars, routes, deployment, and conventions.
- Do not make speculative fixes. Trace the root cause before patching.
- Keep edits narrow and relevant to the request.
- Preserve the existing architecture: React + Vite frontend, Express API, Drizzle/Postgres schema, and generated API client patterns.
- Prefer the smallest possible change that solves the issue and verify it with the relevant command.

## Repo-specific priorities

### Frontend work
- Work in the frontend package under [artifacts/birla-school](artifacts/birla-school).
- Respect routing in [artifacts/birla-school/src/App.tsx](artifacts/birla-school/src/App.tsx).
- Keep page structure, brand styling, and admin flows consistent with the existing school site.
- Preserve the API env behavior: chatbot and generated client must continue to respect `VITE_API_BASE_URL` and local fallback behavior.

### Backend work
- Work in [artifacts/api-server/src](artifacts/api-server/src) for route logic, auth, and middleware.
- Keep auth, validation, and rate limiting consistent with the existing Express API patterns.
- If schemas or API contracts change, update the relevant contract and generated client paths instead of hand-patching generated output.

### Data and schema work
- Use the Drizzle schema under [lib/db/src](lib/db/src) and push schema changes through the repo’s standard command.
- Do not hand-edit database state or skip the repo’s schema workflow.

### Deployment and env work
- Keep Vercel/Render split behavior in mind: frontend builds on Vercel, API runs on Render, and `VITE_API_BASE_URL` is required in production.
- Preserve environment-variable semantics documented in [AGENTS.md](AGENTS.md).
- Do not commit secrets or add new credentials without checking repo policy.

## Validation requirements

- Run the project typecheck after code changes: `pnpm run typecheck`.
- If the task changes build behavior or deployment configuration, validate the relevant command before finishing.
- Do not claim completion without fresh verification output.

## Working behavior

- Start by identifying the exact request and the most likely files involved.
- Read only the exact files needed to confirm the fix or feature.
- Use surgical edits and avoid broad refactors unrelated to the task.
- Prefer implementation patterns already used in the repo instead of introducing new conventions.
- Preserve user-facing text quality and avoid noisy comments; where copy is user-facing, keep it natural and practical.

## When to use this agent

Choose this agent for:
- BOMIS frontend pages, components, and styling updates
- admissions / contact / inquiry form fixes
- admin dashboard and content management work
- API route or auth changes
- chat, gallery, faculty, or stats handling
- schema updates and deployment configuration changes
- bug fixes that involve both the frontend and the backend

Prefer the default agent for unrelated repo tasks outside this website monorepo.

## Helpful prompts

- “Add a new faculty listing field and update the admin form and API validation.”
- “Fix the inquiry submission flow so it sends correctly in production and still saves to the database.”
- “Update the chat UI to use the correct API base while keeping local dev proxy behavior.”
- “Add a new dashboard stat and expose it through the backend route and admin page.”
- “Review the current Vercel/Render setup and identify any remaining deployment issues.”

## Edge guidance

- Follow the project’s existing stack and naming: the real frontend package is `@workspace/birla-school`, not the older `bright-school` naming.
- Keep branding consistent with the school website and orange theme (#F15A29).
- Do not remove or bypass role protections in admin flows.
- When a change affects API contracts, check whether the generated client or schema should be updated rather than hand-editing generated code.
